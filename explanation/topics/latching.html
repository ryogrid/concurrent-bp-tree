GO B+ TREE / CONCURRENCY PRIMER

コードを読む前に：クラブラッチング

親を離す前に子をつかむ。必要なページだけを短時間守り、木全体を止めずに進む。

B+木では、あるスレッドがページを読んでいる間にも、別のスレッドが分裂やマージによってページの内容や接続を変えようとします。親を先に解放してから子を取りに行くと、その間に選んだ子が移動・解放されるかもしれません。そこで使うのがラッチクラビング（latch crabbing、ラッチカップリング）です。

蟹が片方のはさみを離す前に、もう片方で次の足場をつかむように、次のページをラッチしてから現在のページを解放します。ラッチはページのメモリ上の構造を守る短時間の同期です。トランザクションの分離性を提供する行ロックや、永続性を提供するWALとは役割が違います。

RとWの互換性

先に保持中新しいR（共有）新しいW（排他）
なし取得できる取得できる
R同時に取得できるRの解放を待つ
WWの解放を待つWの解放を待つ

GetとRangeScanはRラッチを使い、PutとDeleteはWラッチを使います。R同士は同じページを同時に読めます。Wは内容を書き換えるため、そのページではほかのR/Wと同時に保持できません。ページが違えばW同士でも並行できます。

縦に下降するときの4ステップ

現在ページを保持ルートまたは親をR/Wラッチし、分離キーから進む子を決める。
子をpinしてラッチfetchでフレームをpinし、親を保持したまま子のR/Wを取る。
解放可否を判断読み取りなら常に親を解放。書き込みなら、子が安全な場合だけ不要な祖先を解放する。
子を現在位置にする親はunlockしてからunpinする。同じ手順を葉まで繰り返す。
rootMu（ルート特定）→親ページ→子ページ→必要なら兄弟を左から右

rootMuは「ルートがどのページか」と高さを守る専用ラッチです。ページ内容を守るR/Wラッチとは別物です。ページを取得するときはfetch（pin）→ latch、手放すときはunlatch → unpinの順です。ラッチしたままunpinすると、使用中のフレームが別ページに再利用される危険があります。

この実装のrootMuは、GetではルートページのR取得後に解放します。Put/Deleteでは、開始時のルートがその操作に安全なら早期解放し、それ以外は操作終了まで保持します。ページラッチを解放してもrootMuを保持する場合があります。図の下部と各スレッドの保持一覧で区別できます。

ページ割当・解放のmetaMu、バッファ管理のpool.muは短い管理区間に使います。metaMuを保持したままページラッチやrootMuを取りません。pool.muを保持したまま別のラッチを待ちません。図ではこれらの管理区間とpinの増減を省略し、ページラッチとrootMuを表示します。

書き込みでは「安全な子」まで祖先を保持する

Putに対して安全

count < Max。1件増えても分裂しないため、構造変更はこの子より上へ伝わりません。子のW取得後、祖先を解放できます。

Deleteに対して安全

count > Min。1件減ってもアンダーフローしないため、借用・マージは不要です。子のW取得後、祖先を解放できます。

子が安全でなければ、分裂またはマージが親へ伝わる可能性があります。その場合は子だけでなく、変更を受け止める親・祖先のWラッチも保持したまま下降します。安全な子に到達した時点で、それより上の祖先をまとめて解放します。子が安全でなくても、その親が安全なら、親より上の祖先は不要です。借用・マージは同じ親の子同士で行います。葉リンクで隣接しているだけでは兄弟とは限りません。

横へ進むときは左から右

範囲走査は現在の葉をR保持したまま、nextLeafPIDが指す右の葉をRラッチし、それから現在の葉を解放します。これにより分裂途中のキーを飛ばしません。複数ページを取る順序を左から右に統一すると、互いに逆方向を待つデッドロックを防げます。

削除対象が右端の葉の場合は左兄弟が必要になり、通常の順序とは逆向きになります。この例外では左の葉を待たずにTryLockします。失敗したら削除したキーと値を戻し、全ラッチを解放してルートから再試行します。内部ノードの左兄弟は、水平走査の対象ではないため、共通の親をW保持した状態で取得します。

可視化の見方　T1とT2は別スレッド（Goではgoroutine）です。ページ上のT1:R/T2:Wが保持中のラッチ、赤い破線の「待機」が取得要求です。Rは青、Wは赤で示し、スレッド名で所有者を区別します。「次へ」で取得・解放を1つずつ進めてください。これは実装に沿った代表的な実行順のモデルで、全スケジュールの証明や実スレッドの実行ではありません。横長の木は横スクロールできます。

1. 2つのGet：Rを共有する

同じルートを読む時間が重なってもR同士は両立します。子を確保して親を放した後は、左右の部分木を独立に進みます。

2. 同じ葉のGetとPut：Wが待つ

読み取り中の葉へ書き込むことはできません。GetがRを解放してからPutがWを取得するので、途中の値を読むことはありません。

3. 別の葉への2つのPut：安全な祖先を早期解放する

ルートでは一時的に直列化されますが、安全な子へ降りたスレッドはルートをすぐ解放します。その後は別の葉を同時にW保持できます。

4. RangeScanとDelete：TryLockで待機サイクルを切る

走査が左葉を持って右葉を待ち、削除が右葉を持って左葉を待つと循環します。削除側が左葉で待たずに戻ることで、両方が進めます。

5. 満杯の葉へのPutとGet：分裂が終わるまで親を保持する

今度は右端の葉が満杯です。T1は葉を分けて親の分岐を更新するまで親のWを保持します。T2は親のRで待ち、更新後の分岐を読んでから子へ進むため、途中の未接続ノードへ進みません。

この規則で何が保証されるか

  • 親から選んだ子が、ラッチの空白時間に分裂・解放されることを防ぐ。
  • 同じページの書き込みと読み書きを直列化し、途中状態を観測・上書きしない。
  • 安全な子で祖先を解放し、関係のない部分木の操作を並行させる。
  • 上から下、左から右という順序とTryLock再試行により、待機の循環を作らない。

次の章から、ここで見た規則がGoコードのどの行に対応するかを、1操作ずつ確認します。

ラッチは木の構造と短い読み書きを保護します。RangeScan全体のスナップショット、トランザクション分離、飢餓がないことまでは保証しません。実装では競合時に再試行上限へ到達するとエラーを返す場合があります。
